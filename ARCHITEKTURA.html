Enterprise AI Agent Platform

Architektúra-dokumentum — governance-központú, több-tenantos AI-agent orkesztrációs platform
Kódbázis: enterprise-ai-agent-platform Fő alkalmazás: app/ (Next.js App Router) Nyelv: TypeScript (strict) Generálva: 2026-07-07 Módszer: kódbázis-elemzés (source, schema, routes, DI-gyökér, tesztek)

1. Executive summary

Ez a rendszer egy vállalati AI-agent platform: célja, hogy szervezeti folyamatokat (pl. tudásbázis-kérdések megválaszolása, dokumentum-előállítás, connector-onboarding, monitoring) felügyelt, auditálható AI-agentekkel automatizáljon. A kulcsszó a governance: minden agent-akció egy központi engedélyező kapun (Tool Broker) megy át, minden művelet megváltoztathatatlan, hash-láncolt audit-naplóba kerül, és az érzékeny, „világba kiható” lépések (pl. e-mail küldés, éles változtatás) emberi jóváhagyáshoz vagy kötelező döntési kapukhoz vannak kötve.

Egy nem technikai stakeholder számára a rendszer három dolgot ad:

  • Control Plane — admin/operátor felület: agentek, folyamatok (playbookok), ticketek, jogosultságok, connectorok, monitorok és az audit-napló kezelése.
  • Agent-futtató réteg — az agentek elszigetelt „harness” környezetben futnak, és csak a platform két átjáróján (modell-átjáró + eszköz-bróker) keresztül férnek a modellekhez és eszközökhöz.
  • Sandbox — citált tudásbázis-válaszok és agent által generált HTML-riportok biztonságos előnézete/exportja.

Technológiai alap: Next.js 16 (App Router) + React 19 + TypeScript, PostgreSQL (Neon) Prisma ORM-mel, Clerk (opcionális) humán-auth-tal, és több LLM-szolgáltatóval (ChatGPT OAuth-híd, Google Gemini, OpenRouter) egy egységes Model Gateway mögött. A háttérfeldolgozás egy esemény­vezérelt Dispatcher workeren és Google Cloud Run harness-jobokon fut.

Egy mondatban Governance-first, több-tenantos, moduláris monolit, amely LLM-agentek munkáját brókereli, kapuzza és auditálja — a bizalom nem az agentben, hanem a körülötte lévő platform-kontrollokban van.

2. Rendszeráttekintés

Alkalmazás típusa: biztos szerveroldali renderelésű moduláris monolit Next.js App Routerrel — egyetlen deploy-olható webalkalmazás, amelyben a UI (React Server/Client Components), a REST/agent API-k (route handlerek), a szerver-akciók és a teljes üzleti logika (src/domain) együtt él. Mellette különálló háttérprocesszek futnak: a Dispatcher worker és a konténerizált agent-harness.

Tipikus feldolgozási folyamat (folyamat-ticket)

  1. Operátor a Control Plane-en elindít egy Folyamatot (ProcessDefinition) vagy létrehoz egy ticketet (server action → ProcessService/TicketService).
  2. A folyamat lépéseihez ticketek jönnek létre, szerep→agent feloldással; a ticket ready lesz, a repo pg_notify('dispatch_ticket_ready')-t küld.
  3. A Dispatcher felveszi, dispatch-lockot szerez, ellenőrzi a budgetet, és elindítja a harnesst (lokálisan a wiki/general runtime, vagy Cloud Run Job).
  4. Az agent a Model Gateway-en át hív modellt, és a Tool Brokeren át használ eszközöket (minden hívás engedélyezve + auditálva).
  5. Az eredmény a ticket-workspace-be / board_write-on át kerül; a TicketStateMachine kényszeríti a kapukat, és — kapu esetén — emberi jóváhagyásra (awaiting_human) állítja a ticketet, vagy továbblépteti a folyamatot.

5. Modulok és felelősségi körök

A domain modulok DI-vel, a domain/index.ts kompozíciós gyökérben kötődnek össze, és a services objektumon keresztül érhetők el. Az alábbiakban a legfontosabbak. biztos

Tool Broker központi, kritikus

Szerep: Az egyetlen kapu, amelyen keresztül agentek eszközöket (~40 tool) használnak. Minden hívásnál: aktor→tenant feloldás, engedélyezés (AllowlistAuthorizer: capability-katalógus + connector-grant + tenant-boundary), speciális kapuk (pl. gmail_send emberi jóváhagyás, board_write ticket-tulajdon, web_search policy), majd végrehajtás és audit + ToolCall rögzítés.

Fő fájlok

  • src/domain/tool-broker/tool-broker-service.ts (~3700 sor: ToolBrokerService + AllowlistAuthorizer)
  • src/lib/tool-capability-catalog.ts — a tool→capability leképezés

Kapcsolódó modulok

  • Be: agent runtimes (wiki/general/chat), agent tools REST route
  • Ki: Ticket, ConnectorGrant, FileEditor, SandboxApp, SandboxVersioning, WebSearch/WebFetch, KnowledgeBase, Audit
FigyelemEz a fájl ~3700 soros „isten-objektum” — a legmagasabb módosítási kockázat. Tenant-izolációs rése korábban javítva lett (l. delegációs/agent-ág), a change-eket mindig teszttel (test:tool-broker-*) fedd le.

Model Gateway kritikus

Szerep: Egységes, OpenAI-kompatibilis LLM-hozzáférés. Routing (melyik modell), budget-plafon (per-ticket guardrail + napi cap), sensitivity-router (mit szabad külső modellnek), költségbecslés (model.pricing), és minden hívás ModelCall + audit rögzítése. Providerek: ChatGPT OAuth-híd, Gemini, stub, OpenRouter (env).

Fő fájlok

  • src/domain/gateway/model-gateway.ts, routing-engine.ts, budget-engine.ts, sensitivity-router.ts, chatgpt-oauth-bridge.ts, gemini-provider.ts, oauth-token-store.ts

Dispatcher háttér

Szerep: Nem-LLM worker, amely a ready ticketeket harness-futásra indítja. Esemény­vezérelt (LISTEN/NOTIFY) + 30 mp cron biztonsági háló; dispatch-lock, budget-cap, timeout-watchdog, launcher-választás (local-wiki / docker-local / cloud-run-job).

Fő fájlok

  • src/domain/dispatcher/dispatcher-service.ts, cloud-run-job-launcher.ts, docker-local-harness-launcher.ts, run-dispatch-cycle.ts
  • scripts/dispatcher-worker.ts (belépési pont)

Playbook / Process runtime összetett

Szerep: Háromszintű modell — Playbook (V2, verziózott spec) → Folyamat (ProcessDefinition: publikált verzióra PIN-elt, konfigurált definíció) → Futás (ProcessInstance + StepInstance + DelegationEdge). A TicketStateMachine a szerveroldali kapu-kényszerítő: a step-átmenetek, gate-ek, output-szerződés és RBAC-role itt dől el; agent-kimenet SOHA nem léphet át blokkoló emberi kaput.

Fő fájlok

  • src/domain/playbook/: playbook-v2-service.ts, process-service.ts, process-definition-service.ts, ticket-state-machine.ts, playbook-compiler.ts, playbook-validator.ts, playbook-simulator.ts, playbook-diff.ts, playbook-pack.ts, playbook-author-agent.ts, suitability.ts
  • Tiszta magok: src/lib/playbook-v2/ (runtime, step-payload)

Ticket domain-mag

Szerep: A munka atomi egysége. TicketService a nem-playbook ticketeknél; a playbook-ticketek a TicketStateMachine-en mennek. Állapotok: backlog → ready → in_progress → awaiting_human/needs_info → done/rejected (+ approved).

Fő fájlok

  • src/domain/ticket/ticket-service.ts, ticket-type-config.ts

IAM / RBAC és Tenant biztonság-kritikus

Szerep: IamService — szerepek, jogosultságok (RolePermission), erőforrás-grantek (ResourceGrant), meghívók (invitation redeem), tenant-boundary access audit. TenantService — tenant-tagságok, platform-tagság (superadmin), aktív tenant váltása (cookie).

Fő fájlok

Audit biztonság-kritikus

Szerep: Megváltoztathatatlan, hash-láncolt napló (SHA-256, genesis-horgony), append-only DB-triggerrel védve; AuditChainService.verifyChain teljes vagy checkpoint-szegmens ellenőrzés.

6. Modulok közötti kommunikáció

A kommunikáció alapmintái biztos:

  • Direkt függvényhívás + konstruktor-injekció: a domain-szolgáltatások egymást a domain/index.ts-ben kapott referenciákon hívják. A DI kézi (nincs DI-konténer).
  • Repository-absztrakció: minden perzisztencia az interfaces/index.ts szerződésén megy; a szolgáltatások sosem látnak közvetlen Prisma-t (kevés kivétellel, pl. hash-only audit count a broker/index closure-ökben).
  • HTTP/REST: a harnessben futó agent a platformmal két REST-átjárón beszél (Gateway + Tool Broker), Bearer agent-API-kulccsal.
  • MCP stdio bridge: a Goose harness egy platform_broker stdio MCP-hídon proxy-zik a Tool Broker REST felé.
  • Postgres LISTEN/NOTIFY: ticket-készenlét jelzése a Dispatchernek (dispatch_ticket_ready).
  • Adatbázison keresztüli indirekt kommunikáció: a Ticket/ProcessInstance/DelegationEdge táblák a munkafolyamat „üzenetsorai”.
  • Lazy függvény-referencia a körkörös függőségekre: pl. ProcessService ↔ DispatcherService, PlaybookV2Service ↔ PlatformSettingsService — closure-rel feloldva (l. index.ts kommentek).
  • Callback-injektálás: toolBrokerService.setDelegationProcessor(...), setPlaybookTransitioner(ticketStateMachine) — a broker futásidőben kapja a delegáció/állapotgép-hookot.

9. Authentikáció, autorizáció és biztonsági modell

Auth-rétegek

  • Humán auth: Clerk (clerkMiddleware a proxy.ts/middleware.ts-ben). Clerk hiányában DevAuthProvider (dev-fallback, alap szerep operator) — de ha sem Clerk, sem dev-auth nincs engedve, a middleware 503-at ad (fail-closed a request szintjén). biztos
  • Agent auth: Bearer API-kulcs, bcrypt-hash-elve tárolva (AgentApiKey.keyHash); authenticateAgentRequest + scope-ellenőrzés (requireAgentScope, pl. tool:invoke).
  • Harness callback: megosztott token (HARNESS_CALLBACK_TOKEN).
  • Webhook: Clerk signing secret; OAuth callback state.

Autorizáció

  • Tenant-boundary: aktív tenant a session-cookie-ból (active_tenant_id); superadmin „assume tenant” auditált. Minden erőforrás tenantId-hoz kötött.
  • RBAC: RolePermission + hasMinimumRole/requireTenantRole a server actionökben.
  • Capability-gate: az agent-eszközök deny-by-default a Capability táblából; a Tool Broker AllowlistAuthorizer-e dönt.
  • Kötelező kapuk: a TicketStateMachine szerveroldalon kényszeríti — agent-kimenet nem léphet át blokkoló emberi kaput.

14. AI agenteknek szóló kódbázis-térkép

Olvasási sorrend (belépési pontok)

  1. app/README.md + app/AGENTS.md — futtatás, harness, repo-szabályok. Figyelem: az AGENTS.md szerint ez a Next.js verzió eltér a betanított tudásodtól — olvasd a node_modules/next/dist/docs/-ot kód előtt.
  2. src/domain/index.ts — a teljes DI-gráf; ebből látod, mi mitől függ.
  3. prisma/schema.prisma — az adatmodell, a rendszer „szótára”.
  4. src/repositories/interfaces/index.ts — a perzisztencia-szerződések.
  5. A releváns domain-modul + a hozzá tartozó gyökér-*.md feature-spec (ezek nagyon részletesek és §-hivatkozásokkal vannak a kódban is).

Kritikus modulok (nagy hatókör)

  • tool-broker-service.ts, model-gateway.ts, ticket-state-machine.ts, dispatcher-service.ts, iam-service.ts, audit-chain-service.ts.

Implicit szabályok (a kódból/jegyzetekből)

  • Csak a main ágon dolgozz — a projektben nincs feature-branch munkafolyamat.
  • Sub-agentet csak tényleg komplex feladatra használj; sub-agent után mindig git diff (a jegyzetek szerint egy „research-only” agent egyszer eltörte az audit hash-láncot).
  • A propose-not-apply minta kötelező az agent-szerzőknél (playbook/provisioning): a modell kimenete CSAK adat, a determinisztikus validátor a kapu.
  • Audit: nyers URL/query/tartalom SOHA nem megy a naplóba — csak hash + metaadat.
  • Kerüld a sok ad-hoc npx tsx -e scriptet: idle Neon-kapcsolat-szivárgást okoz (a teszt „lefagyottnak” tűnik).

Stabil vs. gyakran változó

Stabil interfészek repositories/interfaces, hash-chain.ts, auth-context szerződés, OpenAI-kompatibilis gateway-kontraktus, tool-broker invoke() szignatúra.
Gyakran mozgó / kockázatos tool-broker-service.ts (isten-objektum), domain/index.ts (kényes DI-sorrend, lazy closure-ök), Playbook/Process runtime, seed.

Hasznos keresőkifejezések

  • input.tool === ' (tool-elágazások), audit.append( (naplózási pontok), requireTenantRole/requireAgentScope (auth-gate), evaluateTicketTransition (kapu-mag), policyDecision (engedélyezési döntések), tenantId (izoláció).
Anti-pattern / veszélyes módosítás Ne kerüld meg a Tool Brokert közvetlen connector-hívással; ne írj közvetlen Prisma-t domain-service-ben; ne módosítsd az audit hash-formulát a verifyChain verzió-kezelése nélkül; ne léptess ticketet a TicketStateMachine megkerülésével (megsértheti a kötelező emberi kaput).

18. Összefoglaló

  • Fő szerkezet: egyetlen Next.js moduláris monolit (UI + API + domain + repositories) Postgresre, mellette Dispatcher worker és konténerizált agent-harness. A domain-gráf a domain/index.ts kézi DI-gyökérben áll össze.
  • Legfontosabb modulok: Tool Broker (eszköz-engedélyezés), Model Gateway (LLM), TicketStateMachine + Process/Playbook runtime (kapuzott orkesztráció), IAM/Tenant (izoláció), Audit hash-lánc (integritás).
  • Módosításkor figyelj: tenant-boundary mindenütt; deny-by-default capability/egress; a kötelező emberi kapuk megkerülhetetlensége; audit rögzítés minden policy-döntésnél; a DI init-sorrend és a Tool Broker mérete.
  • Hol kezdj: új fejlesztő/AI agent → app/README.md + AGENTS.md → domain/index.ts → prisma/schema.prisma → az érintett domain-modul és a hozzá tartozó gyökér feature-spec (*.md). A tesztet a megfelelő scripts/*.test.ts + test:* scripttel futtasd, lehetőleg stub DATABASE_URL-lel.
