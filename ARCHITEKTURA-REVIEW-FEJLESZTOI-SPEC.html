1.1 — Közös fail-closed resolver

Új, egyetlen helyre koncentrált feloldó, hogy a minta ne szóródjon szét. Prod alatt env hiányában induláskor dob; nem-prod alatt determinisztikus dev-defaultot ad, de warn-ol.

új: app/src/lib/crypto/secret-resolver.ts 
const isProd = process.env.NODE_ENV === 'production'

/**
 * Fail-closed titok-feloldás. Prod alatt kötelező az env; hiányában
 * a folyamat induláskor leáll (nem fut kompromittált dev-defaulttal).
 */
export function resolveSecret(
  names: string[],           // fallback-lánc, pl. ['OAUTH_STATE_SECRET','WRITE_GATE_SECRET']
  devDefault: string,        // CSAK nem-prod alatt használt determinisztikus default
): string {
  for (const n of names) {
    const v = process.env[n]
    if (v && v.length > 0) return v
  }
  if (isProd) {
    throw new Error(
      `[secret-resolver] Kötelező titok hiányzik prod alatt: ${names.join(' | ')}. ` +
      `Állítsd be a Secret Managerben és az apphosting.yaml-ban.`,
    )
  }
  console.warn(`[secret-resolver] DEV default használatban: ${names[0]} (NE használd prod-ban)`)
  return devDefault
}

Lelet: F3Cél: a policyDecision/metadata/payload-ref is a hash alatt legyen, visszafelé kompatibilisen
✓ Elkészült — 2026-07-07 (main working tree, nincs commitolva)
  • Verzió-önleíró hash: a hash-chain.ts kapott egy computeAuditHashV2-t, ami "2:" előfejjel tér vissza. A verzió magában a tárolt hash-stringben utazik → nincs szükség séma-oszlopra (a WP-5 migrációtól függetlenül szállítható), és a láncba kötött prevHash a teljes, előfejes stringet hordozza.

  • Verzió-érzékeny verify: az AuditChainService.verifyChain soronként a tárolt hash előfeje alapján választ formulát (parseAuditHashVersion) — a régi v1 sorok v1-gyel, az újak v2-vel. Egy v2 sort nem lehet a v1 formulával (ami a metadatát figyelmen kívül hagyja) átverni.
  • Írás + repair átkötve: a PostgresAuditRepository.append mostantól v2-t ír (a hash a deriveAuditAttribution kimenetével EGYÜTT számolódik); az audit-backfill.ts reconcile is verzió-érzékeny, nem minősíti vissza a v2 sorokat.
  • Teszt: scripts/audit-log.test.ts +6 új eset (v2 lánc, metadata/policyDecision/output_ref tamper, vegyes v1+v2 lánc, v1-átverés elleni invariáns) — 23/23 zöld. tsc tiszta, eslint 0 hiba az érintett fájlokra.
Hátra (nem-kód): a hashVersion oszlop bevezetése nem szükséges ehhez a megoldáshoz; ha később mégis kell (analitika), az WP-5 migráció. A meglévő láncok visszamenőleg érvényesek maradnak (v1 sorok nincsenek rehash-elve).

Probléma: a main computeAuditHash csak a vázat fedi; a policyDecision (deny→allow), payload-ref és metadata utólagos átírása a lánc-ellenőrzést nem bukná.

mód: app/src/lib/crypto/hash-chain.ts — computeAuditHash 
// Verzió-előtag a hash-stringben → verzió-érzékeny verify, visszafelé kompatibilis lánc.
export function computeAuditHash(params: {
  seq: bigint; prevHash: string
  actorType: string; actorId: string | null
  action: string; targetType: string; targetId: string | null
  createdAt: Date
  // ÚJ, opcionális mezők (v2):
  policyDecision?: string | null
  payloadRef?: string | null
  metadata?: unknown
}): string {
  const canonical = JSON.stringify({
    v: 2,                                   // verzió-diszkriminátor
    seq: params.seq.toString(),
    prevHash: params.prevHash,
    actorType: params.actorType,
    actorId: params.actorId ?? '',
    action: params.action,
    targetType: params.targetType,
    targetId: params.targetId ?? '',
    createdAt: params.createdAt.toISOString(),
    policyDecision: params.policyDecision ?? '',
    payloadRef: params.payloadRef ?? '',
    metadata: stableStringify(params.metadata ?? null),  // kulcs-rendezett, determinisztikus
  })
  return createHash('sha256').update(canonical, 'utf8').digest('hex')
}
Kritikus: verifyChain verzió-kezelés A AuditChainService.verifyChain a meglévő (v1) sorokat a régi formulával, az új sorokat a v2-vel ellenőrizze. Diszkriminátor: a sor createdAt-ja a v2 bevezetése előtt/után, vagy egy explicit hashVersion oszlop az AuditLog-on (ajánlott — determinisztikus). Ne backfilleld a régi hasheket: a lánc integritása pont attól él, hogy a régi hasheket nem írjuk át.

Séma: ha hashVersion Int @default(1) oszlopot vezetsz be az AuditLog-ra → WP-5 migráció (addig db push dev-en). Az append-only trigger továbbra is tiltja az UPDATE/DELETE-et.

Elfogadási kritérium
  • Új v2 sor hash-e fedi a policyDecision + payloadRef + metadata mezőket.
  • verifyChain vegyes (v1+v2) láncon zöld; egy v2-sor bármely fedett mezőjének manuális átírása → verify bukik.
  • Meglévő scripts/audit-log.test.ts kiterjesztve (referencia: security/audit-hash-full-coverage ág +141 sor).

/** Deny-by-default CSP az agent-generált HTML-hez. `allow-scripts` a working
 *  appokhoz, de allow-same-origin NÉLKÜL → az origin opaque, nincs platform-hozzáférés. */
export const SANDBOX_CSP =
  "sandbox allow-scripts; default-src 'none'; " +
  "img-src data: blob:; style-src 'unsafe-inline'; script-src 'unsafe-inline'; " +
  "font-src data:; base-uri 'none'; form-action 'none';"

export function sandboxHtmlHeaders(): Record<string, string> {
  return {
    'Content-Type': 'text/html; charset=utf-8',
    'Content-Security-Policy': SANDBOX_CSP,
    'X-Content-Type-Options': 'nosniff',
    'X-Frame-Options': 'SAMEORIGIN',
  }
}

Hátra (nem-kód / üzemeltetés): a meglévő prod/dev/test Neon DB-k egyszeri migrate resolve --applied 0000_init baseline-elése (különben a migrate deploy újrafuttatná a 0000-t) — teszt-branchen próbálva elsőként.

Probléma: Ma nincs prisma/migrations/; minden séma db push + ad-hoc db:apply-*/db:backfill-* scriptekkel megy → drift-veszély.

Lépések

  1. Baseline generálás a jelenlegi sémából (adatvesztés nélkül, meglévő DB ellen): 
    cd app
npx prisma migrate diff \
  --from-empty --to-schema-datamodel prisma/schema.prisma \
  --script > prisma/migrations/0000_init/migration.sql
npx prisma migrate resolve --applied 0000_init   # meglévő prod/dev DB-n
  2. Ad-hoc SQL beemelése migrációkba: az apply-audit-append-only-trigger, apply-kb-chunk-fts-index, apply-agent-api-key-expires-at és a WP-2 hashVersion oszlop → külön migrációk (0001_audit_append_only, 0002_kb_fts, …). A backfill-scriptek maradhatnak külön (adat, nem séma).
  3. Workflow-váltás: fejlesztésben db:migrate (nem db:push); a CI (WP-4) egy ephemeral Postgres ellen futtatja a migrate deploy-t + a stub-teszteket.
  4. Dokumentálás: app/AGENTS.md/README.md frissítése: „sémaváltás = új migráció, nem db push”.
Vigyázat — éles DBA baseline-t migrate resolve --applied-del kell „már alkalmazott”-nak jelölni a meglévő prod/dev/test DB-ken, különben a migrate deploy újra lefuttatná. Teszt-branch (Neon) ellen próbáld ki elsőként.
Elfogadási kritérium
  • Létezik prisma/migrations/ baseline-nal; friss DB migrate deploy-jal a jelenlegi sémát adja.
  • Meglévő környezetek resolve-val baseline-eltek, nincs újrafuttatás.
  • CI ephemeral DB ellen futtatja a migrációkat.
  • Az ad-hoc SQL-triggerek/indexek migrációkban (nem csak scriptben).
