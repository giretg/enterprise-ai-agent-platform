ZPK Agent System Specification

Detailed functional and technical specification for a Langflow-based agent system that generates and exports a Zone PIN Key under an existing Zone Master Key using a controlled payShield 10K host-interface tool module.

1. Scope and Design Principles

The first implementation scope is deliberately narrow: generate a Zone PIN Key and export it encrypted under an already existing Zone Master Key for a selected target party and environment.

Initial operation: GENERATE_EXPORT_ZPK_UNDER_ZMK.

In Scope

  • Request intake through a Sec Officer agent.
  • Clarification of business request data.
  • Target party lookup and cryptographic profile resolution.
  • Existing active ZMK lookup from the key registry by target party, environment, and KCV-based key identity.
  • ZPK generation and export under the resolved ZMK.
  • Human approval before execution.
  • Execution through a local Python module running under Langflow.
  • TCP/IP communication with the payShield 10K host interface.
  • Storage of encrypted key cryptograms, KCVs, metadata, and operation results in PostgreSQL.
  • Email notification for pending approvals, missing prerequisites, missing target-party profiles, multiple ZMK candidates, failed execution, and closure.

Out of Scope

  • HSM console operations.
  • Key component printing.
  • Clear key component handling.
  • Test-to-production or production-to-test key migration.
  • Emergency exception processing.
  • Direct raw HSM command entry by users or agents.

Core Principles

  • The agent initiates the operation, but a human approver authorizes execution.
  • The HSM tool module assembles the host command from validated structured input and the approved command template.
  • The agent must not send arbitrary command strings to the HSM.
  • The registry is the authoritative source for key metadata, target-party profiles, target-party to ZMK assignments, KCV-based key identification, and key lifecycle status.
  • Encrypted working-key cryptograms and key blocks may be stored in the database because their cryptographic protection is provided by the HSM key hierarchy, for example a key encrypted under the LMK hierarchy or a key exported under a ZMK. The LMK itself is never exported, never represented by a public cryptogram, and never stored outside the protected HSM environment. Database access control remains necessary for auditability and operational control.

Trust Boundaries

Agent to database Agents read and write ticket, registry, profile, and audit data. Role-based database access, stored procedures or service layer, full audit events.

3. Agent Roles

Sec Officer Agent

The Sec Officer agent is the only external-facing agent. It receives the request, creates or updates the ticket, coordinates specialist agents, and presents the final execution plan for approval.

  • Collects requester identity, unit, target party, environment, business reason, activation date, and intended usage.
  • Determines whether the request belongs to the ZPK generation/export flow.
  • Routes console-only or component-printing requests to a human-only manual process.
  • Coordinates registry lookup, policy checks, execution planning, approval, execution, and closure.

Requirement Clarifier Agent

This agent separates business clarification from cryptographic parameter clarification.

Missing Data Type Clarification Target Example
Business request data Requester Missing target party, business reason, requested activation date.
Cryptographic profile data Approver or designated security specialist Missing default ZPK algorithm, key length, scheme, KCV format.
Prerequisite key data Approver notification No active ZMK exists for the target party and environment, or multiple possible ZMKs are assigned and KMO selection is required.

Registry Agent

  • Resolves the target party profile.
  • Finds active ZMK candidates for the target party and environment through the target-party to key assignment table.
  • Creates the ZPK key record after successful HSM execution.
  • Stores the encrypted ZPK cryptogram, KCV, protection key reference, lifecycle status, and ticket linkage.

Policy Agent

  • Validates environment separation.
  • Rejects test-production key migration attempts.
  • Rejects raw command execution requests.
  • Confirms that the intended usage is valid for the ZPK operation.
  • Confirms that the selected ZMK is active, assigned to the target party, and belongs to the same environment.
  • Requires human approval before the HSM tool can execute.

HSM Planning Agent

This agent prepares a structured execution plan. It does not assemble the final payShield host command.

Audit Agent

The audit agent prepares human-readable evidence from immutable database events. It is not the source of truth; the event tables and HSM result records are.

4. ZPK Workflow

Happy Path

  1. Requester submits a ZPK generation/export request.
  2. Sec Officer agent creates a ticket in DRAFT status.
  3. Requirement Clarifier validates requester, unit, environment, target party, intended usage, business reason, and activation date.
  4. Registry Agent resolves the target party by target_party_code.
  5. Registry Agent finds active ZMK candidates for the same target party and environment.
  6. If exactly one active ZMK candidate exists, the workflow uses it automatically. If multiple active ZMK candidates exist, the workflow asks the KMO to select the correct ZMK. The PM cannot perform this selection because PM users cannot access the key registry.
  7. Registry Agent loads the target party cryptographic profile.
  8. If profile fields are complete, ticket moves to READY_FOR_POLICY_CHECK.
  9. Policy Agent evaluates mandatory controls.
  10. HSM Planning Agent creates the execution plan.
  11. Ticket moves to READY_FOR_APPROVAL.
  12. Email notification is sent to the approver.
  13. Approver reviews the web UI and approves the execution.
  14. Ticket moves to APPROVED.
  15. HSM tool validates ticket status, approval, input schema, environment configuration, and module integrity.
  16. HSM tool assembles the payShield host command from an approved template.
  17. HSM tool sends the command over TCP/IP to the configured payShield host endpoint.
  18. HSM tool parses and validates the response.
  19. Registry Agent creates a ZPK record with encrypted key value, KCV, protection ZMK, and HSM operation reference.
  20. Ticket history is updated with the structured result.
  21. Email notification is sent to the requester and approver. The PM notification includes the generated ZPK cryptogram protected by the LMK hierarchy, the generated ZPK cryptogram exported under the selected ZMK, and the ZPK KCV.
  22. Ticket moves to CLOSED.

Ticket Statuses

  • DRAFT
  • CLARIFICATION_REQUIRED
  • CRYPTO_PROFILE_REQUIRED
  • PREREQUISITE_MISSING
  • READY_FOR_POLICY_CHECK

  • APPROVED
  • EXECUTION_STARTED
  • EXECUTION_FAILED

5. Request Model

The requester is expected to know the business intent, not low-level cryptographic parameters. The system resolves cryptographic parameters from the target party profile or asks the approver to complete them.

Requester-Supplied Fields

Field Required Description Validation
requester_name Yes Name of the requester. Non-empty.
requester_email Yes Email address for notifications. Valid email format.
requester_unit Yes Unit of the requester. Must map to an allowed internal unit or be explicitly recorded.
requesting_company_or_business_unit Yes Company or business unit represented by the request. Non-empty.
environment Yes Execution environment. TEST or PROD.
operation Yes Requested operation. For MVP: GENERATE_EXPORT_ZPK_UNDER_ZMK.
target_party_name Yes Human-readable target party name. Must match or help resolve target_party_code.
target_party_code Yes Registry identifier of the target party. Must exist or trigger target party creation process.
intended_usage Yes Business and cryptographic usage intent. Included now to support future key types. For ZPK MVP: must be compatible with online PIN interchange.
business_reason Yes Why the key is needed. Non-empty; stored in ticket history.
requested_activation_date Yes Requested date from which the generated key should be considered active. Valid date; no past date for production unless policy allows.

System-Resolved Fields

Field Source Fallback
existing_zmk_key_id Active ZMK registry lookup by target party and environment through target_party_keys. ZMK identity is primarily verified by KCV. If missing, ticket becomes PREREQUISITE_MISSING. If multiple candidates exist, KMO selection is required.
zpk_algorithm Target party crypto profile. Approver supplies value; stored back to profile.
zpk_length Target party crypto profile. Approver supplies value; stored back to profile.
zpk_variant_or_scheme Target party crypto profile. Approver supplies value; stored back to profile.
kcv_format Target party crypto profile or default local rule. Approver supplies value.

6. Key Registry

The key registry is the authoritative source for key inventory. It records encrypted working-key cryptograms, key blocks, cryptographic metadata, lifecycle status, ownership, environment, and protection relationships. It does not record the LMK itself; the LMK is the root of the HSM key hierarchy and exists only inside the protected HSM environment.

Key Types in MVP

Key Type Meaning MVP Role
ZMK Zone Master Key. Must already exist and be active. Used as the export protection key. It is normally created manually outside this workflow and then registered in the key registry by a KMO.
ZPK Zone PIN Key. Generated by the HSM and exported encrypted under the selected ZMK.

ZMK Identification and Target Party Assignment

A ZMK is primarily identified operationally by its Key Check Value. The registry also assigns an internal key_id for database reference and audit traceability, but KCV must be visible to the KMO during selection, approval, and evidence review.

Target parties and ZMKs have a many-to-many relationship. One target party may have multiple active or historical ZMKs, and one ZMK may be assigned to multiple target parties depending on the operating model. Therefore, ZPK generation cannot always resolve the ZMK from the target party alone.

Target parties and ZPKs have a stricter relationship. A target party may have multiple ZPKs, but a ZPK belongs to exactly one target party. Therefore, the registry must prevent assigning the same ZPK to multiple target parties.

Case System Behavior
No active ZMK assigned to the target party and environment. Set ticket status to PREREQUISITE_MISSING and notify the KMO. ZPK generation cannot continue.
Exactly one active ZMK assigned. Use that ZMK as the protecting key and include its key_id and KCV in the execution plan.
Multiple active ZMKs assigned. Ask the KMO to select the correct ZMK. The PM cannot select a ZMK because PM users do not have key registry access.

ZPK Ownership Rule

Relationship Cardinality Rule
Target Party to ZMK Many-to-many Multiple target parties may share a ZMK assignment, and one target party may have multiple ZMK assignments.
Target Party to ZPK One-to-many One target party may have multiple ZPKs, but each ZPK may be assigned to one target party only.

Manual ZMK Registration

ZMK creation is a separate manual process outside the ZPK generation/export workflow. After a ZMK exists, a KMO may register it in the key registry so it can be used as a prerequisite for later ZPK export operations.

Minimum registration data:

  • ZMK KCV.
  • Environment: TEST or PROD.
  • Encrypted ZMK representation or key block, if available through the approved operating process.
  • Key scheme, algorithm, and key length where known.
  • Assigned target party or parties.
  • Activation date and status.
  • Manual process reference or evidence reference.
  • KMO who registered the ZMK.

Key Protection Model

Protection Type Description Storage Policy
LMK_HIERARCHY A working-key cryptogram encrypted under the HSM Local Master Key hierarchy or a key derived from that hierarchy. The LMK itself is the root key material inside the HSM protected environment only. The protected working-key cryptogram may be stored in the registry with metadata and KCV. The LMK is never stored, exported, or represented as a registry cryptogram.
ZMK Exported key cryptogram protected under a Zone Master Key. May be stored in the registry and linked to the protecting ZMK.

Target Party Profile

The target party profile stores default cryptographic parameters so requesters do not need to know them. Missing profile values are completed by the approver and then persisted for future requests.

Field Purpose
default_zpk_algorithm Default algorithm for ZPK generation, for example 3DES or AES if supported by the local profile.
default_zpk_length Default key length, for example DOUBLE or TRIPLE.
default_zpk_scheme Key scheme or variant convention required for this target party.
default_zpk_usage Expected usage, for example online_pin_interchange.
default_kcv_format Preferred KCV format for reporting and validation.

Mandatory Tool Checks

  1. Validate the input schema.
  2. Verify that the ticket exists and is in APPROVED status.
  3. Verify that the approval exists, is approved, and belongs to the same ticket.
  4. Verify that the selected ZMK exists, is active, matches the ticket environment, and is assigned to the target party through target_party_keys.
  5. Verify that the environment maps to the correct HSM endpoint.
  6. Run module integrity checks, for example code hash, package version, and template hash.
  7. Assemble the HSM command from an approved internal template.
  8. Send the command over TCP/IP.
  9. Parse the response with strict field validation.
  10. Return structured output only.

Prohibited Tool Behavior

  • Accepting raw HSM command strings from agents or users.
  • Executing without a valid approved ticket.
  • Mixing TEST and PROD configuration.
  • Falling back to a different HSM endpoint after connection failure.
  • Silently retrying an operation that may create another key unless an idempotency design is added.

10. Knowledge Base and Command Catalog

The knowledge base is a separate administrative function. In the current role model, the KMO is also the knowledge administrator for documents, local experience records, and general knowledge content. Command schema and command template administration are separated from the KMO role and assigned exclusively to the HSM Manager during an active Department Head enabled time window. Operational agents consume only approved knowledge artifacts, approved local experience records, and approved command templates.

Design decision: the knowledge base can help the agent understand HSM documentation, but the final TCP/IP message must be created by a deterministic Python builder using an approved command template.

Command Template Management

Command template management is restricted to the HSM Manager role. The HSM Manager account is normally inactive and can operate only during a Department Head enabled time window of at most 120 minutes. Template management includes create, update, delete, retire, and approve actions. Any change to a command template must create an immutable administration event with before and after state.

Action Purpose Control
CREATE Create a new template from an approved command catalog entry. Template starts in DRAFT status and cannot be executed.
UPDATE Modify a draft or create a new version of an existing template. Approved templates should not be edited in place; updates create a new version and new template hash.
DELETE Remove an unused draft template. Only draft templates with no execution history may be deleted.
RETIRE Disable an approved template without deleting its audit history. Retired templates cannot be used for new executions.
APPROVE Make a reviewed template executable by the HSM tool. Approval records template hash, catalog source, approver, and timestamp.

11. Identity, Authentication and Access Control

The system uses a portable, self-contained identity and authorization model controlled inside the Security Department. It does not depend on the corporate identity provider for role assignment or cryptographic-operation authorization.

Design decision: a chat statement such as "I am KMO" or "I am HSM Manager" is not authentication. It is only a claimed role. The system accepts role-sensitive actions only when the current authenticated session belongs to an active user with the required role, permission, and activation state.

Bootstrap Department Head

During system initialization, one Department Head account is created through a controlled bootstrap procedure. This role has a deliberately narrow authority: it can approve KMO appointments and enable the HSM Manager account for a limited time window. It does not automatically receive operational key-management permissions.

Role Authority Explicit Restriction
DEPARTMENT_HEAD Approve or reject KMO appointment requests and enable the HSM Manager account for a specified period up to 120 minutes. Suggested permissions: appoint_kmo, activate_hsm_manager, revoke_hsm_manager_activation. No implicit right to approve key operations, execute HSM tools, edit target-party profiles, or manage command templates.

Operational Roles

Authentication Requirements

  • The system must maintain its own user database, roles, permissions, sessions, authentication events, and KMO appointment records.
  • Every interactive chat or web session must be bound to an authenticated user session before any role-sensitive action is accepted.
  • PM access requires successful login. MFA is not required for PM users in the current scope.
  • KMO access requires successful login and multi-factor authentication.
  • KMO approval of a key operation requires a fresh step-up authentication event before approval is recorded.
  • HSM Manager access requires successful login, multi-factor authentication, and an active Department Head enabled activation window.
  • HSM Manager command template operations require step-up authentication inside the active window.
  • TOTP is an acceptable local MFA method for KMO, HSM Manager, and Department Head users. WebAuthn/FIDO2 can be introduced later as a stronger option.
  • Passwords, if used, must be stored only as slow salted password hashes. Plaintext passwords must never be stored.

Recommended Local Authentication Design

The authentication solution should be portable and self-contained. It should not require a corporate identity provider, cloud identity service, or external authorization system. The preferred design is a local authentication module operated by the Security Department.

Layer Recommendation Reason
User identity Local users table with Department Head bootstrap, KMO appointment workflow, and HSM Manager activation windows. KMO appointment and HSM Manager activation remain under Security Department control.
Primary login Username and password with Argon2id or bcrypt password hashing, or client-certificate login if local PKI is available. Keeps the solution independent and deployable on-premises.
KMO, HSM Manager, and Department Head MFA TOTP is the initial local MFA method. WebAuthn/FIDO2 security key or platform passkey can be introduced later as a stronger option. Provides stronger protection for approval and administrative actions.
TOTP secret protection TOTP seeds and recovery-sensitive authentication secrets are encrypted using the HSM data-encryption capability. Protects authentication secrets while keeping the authentication function separate from payment key operations.
Step-up authentication Required before approve_key_operation, execute_hsm_tool, command template administration, and sensitive registry changes. Prevents stale sessions from authorizing sensitive operations.
Session protection HTTP-only secure session cookies, server-side session storage, idle timeout, absolute timeout, and session revocation. Allows local control and audit of active sessions.
Audit Every login, failed login, MFA event, step-up event, role change, KMO appointment, and HSM Manager activation or revocation is recorded in auth_events. Supports operational review and incident investigation.

Chat Authentication Behavior

The chat interface must never infer role from natural language. It must use the current authenticated session and the authorization database.

User message: "I am KMO" or "I am HSM Manager"

System behavior:
1. Read current authenticated session.
2. Resolve user_id from session.
3. Load active roles and permissions.
4. If required role and permission are present, evaluate any extra activation requirement.
5. For HSM Manager actions, require an active Department Head enabled time window.
6. Otherwise deny the action and ask the user to authenticate or contact the Department Head process.

Bootstrap and Recovery

  • The initial Department Head account is created only during system initialization.
  • Bootstrap credentials or recovery codes must be stored and handled under a documented local ceremony.
  • Department Head replacement must require a controlled administrative recovery procedure and must be audit logged.
  • No system administrator account should be able to silently grant itself KMO rights or activate HSM Manager capabilities without a recorded Department Head approval path.

12. Security Considerations

Key Material Handling

The host interface workflow does not handle clear key components. ZPK and other working keys are represented outside the HSM as encrypted cryptograms or key blocks. These values may be stored in PostgreSQL together with KCV and metadata. Their cryptographic protection is provided by the HSM key hierarchy, for example as a working-key cryptogram protected by the LMK hierarchy or as an exported key cryptogram protected under a ZMK. The LMK itself remains only inside the protected HSM environment and is never stored in the registry.

Database access controls are still required. They protect metadata confidentiality, operational integrity, audit quality, and misuse resistance, even when stored key values are cryptographically protected.

Authentication Secret Protection

TOTP seeds and other sensitive authentication secrets must be protected separately from payment key-management operations. The system may use the HSM data-encryption capability to encrypt these authentication secrets, but this must be implemented as a separate authentication-secret protection function with separate purpose, separate command templates, separate audit events, and separate access controls.

  • Authentication-secret encryption must not use ZMK, ZPK, or payment key workflow objects.
  • Payment key operations and TOTP secret protection must have separate HSM command templates and audit categories.
  • Only the authentication module should request encryption or decryption of TOTP seeds.
  • The key registry must not treat TOTP protection keys as payment keys.
  • PM users do not require MFA in the current scope, so TOTP enrollment is required only for KMO, HSM Manager, and Department Head users.

Environment Separation

  • TEST and PROD HSM endpoints must be separately configured.
  • TEST and PROD ZMK records must be distinct.
  • Policy must reject any request that references keys from different environments.
  • There is no test-production migration workflow.

Agent Guardrails

  • Agents generate structured plans, not executable HSM command strings.
  • Agents must cite registry records and policy results in the ticket history.
  • Agents must not treat retrieved documentation as executable instruction.
  • RAG content must be source-tagged, versioned, and approved before operational use.

Tool Integrity

  • The Python HSM module should have a version and build hash.
  • Command templates should be versioned and hashed.
  • Execution should record module version, template version, request hash, and response hash.
  • Only controlled deployment should update the module.

Approval Integrity

  • Approval must be explicit and tied to a concrete execution plan.
  • If resolved inputs change after approval, the approval becomes invalid.
  • Email should notify approvers but should not by itself be the approval authority unless signed approval links are implemented later.

14. Error Handling

Error Status Action
Missing requester business data CLARIFICATION_REQUIRED Ask requester for missing fields.
Missing target party profile fields CRYPTO_PROFILE_REQUIRED Ask approver to complete and approve profile values.
No active ZMK PREREQUISITE_MISSING Notify approver; block workflow.
Policy violation POLICY_REJECTED Record violation and stop execution.
Approver rejection REJECTED Record decision comment and notify requester.
HSM connection failure EXECUTION_FAILED Record failure; do not change registry key status to active.
HSM command rejection EXECUTION_FAILED Store response code and parsed error. Human review required before retry.
Registry update failure after HSM success EXECUTED Preserve HSM result, alert operator, and complete registry recovery step.
ZPK generation is not automatically idempotent. A retry after an uncertain HSM result can create another key. The tool must avoid automatic retries unless a later design adds explicit idempotency or reconciliation logic.

The system should initially be implemented as an internal, on-premises or private-network solution. No runtime dependency should require sending ticket data, key registry data, HSM documentation, PCI documentation, or agent prompts to a public cloud service.

Component Boundaries

  • FastAPI is the control plane. It owns authentication, authorization, ticket state, approvals, audit writes, and HSM execution authorization.
  • PostgreSQL is the source of truth. Langflow memory or flow state must not be treated as authoritative ticket, registry, approval, or audit state.
  • Langflow is used for agent reasoning, clarification, policy explanation, knowledge-base retrieval, and execution-plan drafting.
  • The HSM tool is deterministic and template-driven. It must not accept raw HSM command text from Langflow, chat, or users.
  • The payShield host interface should be reachable only from the approved HSM tool runtime host or service.

Deployment Options

Option Use Notes
Docker Compose on internal Linux VM Recommended for MVP and controlled internal pilot. Simple deployment model for FastAPI, PostgreSQL, Langflow, and supporting services.
Systemd-managed services Suitable where container runtime is not preferred. Requires more explicit service and dependency management.
Internal Kubernetes or OpenShift Suitable for later production hardening if the organization already operates it. Adds operational complexity; should not be required for the first MVP.

Network Controls

  • PM and KMO browsers access only the internal Web UI/API endpoint over HTTPS.
  • PostgreSQL is not exposed to user workstations.
  • Langflow is not exposed directly to PM/KMO users unless explicitly wrapped by the application.
  • The payShield TCP/IP endpoint is reachable only from the HSM tool runtime.
  • TEST and PROD HSM endpoints must use separate configuration and network controls.
  • No runtime internet access is required for core operation.

MVP Implementation Recommendation

  1. Implement FastAPI, PostgreSQL schema, PM/KMO authentication, and basic ticket lifecycle.
  2. Implement Langflow-based Sec Officer, Requirement Clarifier, Policy, Registry, and HSM Planning flows.
  3. Implement a mock HSM tool for ZPK generate/export behavior and registry updates.
  4. Implement knowledge document ingestion and command catalog approval for the A0/A1 generate/export command.
  5. Implement KMO approval with execution-plan hash binding.
  6. Only after the above is stable, connect the controlled Python HSM tool to the real payShield host interface in TEST.
